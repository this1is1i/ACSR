## Q17: 前端状态管理如何实现？登录状态如何持久化？（2026-06-02）（git: bad2152）

### 数据流

```
登录成功 → setAuth(response)
  ├── token    → Pinia token.value  +  localStorage.setItem('token')
```

## Q18: 用户状态为什么是 32+32+32？这些 32 维怎么算出来的？（2026-06-02）（git: bad2152）

### 结构

```
state = concat(interest[:32], history[:32], kg_vector[:32]) = 96 维
base_state_dim = 64 = interest(32) + history(32)
state_dim = 64 + kg_embedding_dim(32) = 96
```

### 兴趣向量（前 32 维）

用户注册时选的关键词 → `hash(关键词)` → 确定性 64 维向量 → 取前 32 维 → 多关键词按 weight 加权平均 → L2 归一化。

```python
# feature_builder.py:192-217
for tag in tags:
    tag_vec = self._hash_tag(tag["interest_tag"], base_state_dim=64)
    vec += tag_vec * tag_weight
vec /= total_weight
# 最终 build_state 时取 vec[:32]
```

### 历史行为向量（中 32 维）

从 behavior_log 查历史 → 每篇论文的预存 32 维 embedding → 按行为类型加权池化（click=0.5, read=1.0, favorite=2.0, 阅读时长每 60s+0.5 上限+2.0）。

```python
# feature_builder.py:219-279
weights = [0.5, 1.0, 2.0][action] + min(duration/60*0.5, 2.0)
history_vec = np.average(vecs, axis=0, weights=weights)
```

### KG 向量（后 32 维）

用户历史论文在 KG 中的 embedding 取平均。

```python
# kg_embedder.py:69-84
user_kg = np.mean([self._embeddings[pid] for pid in history], axis=0)
```

### 为什么是 32

1. **2 的幂**：GPU 矩阵运算内存对齐优化
2. **三段对齐**：兴趣/历史/KG 各 32 维，拼接后各段权重自然均衡
3. **够用但不大**：10 个原始特征投影到 32 维有足够表达能力
4. **历史一致性**：base_state_dim=64, half=32，后续 KG 沿用此数

## Q19: 投影矩阵 P 的完整机制（2026-06-02）（git: bad2152）

### P 是什么

P 是一个固定的 10 行 × 32 列矩阵，将 10 维结构特征映射到 32 维嵌入空间。

```python
# kg_embedder.py:46-48 & generate_paper_embeddings.py:173
rng = np.random.default_rng(42)  # 固定种子
P = rng.standard_normal((10, 32)) / sqrt(10)  # Xavier 风格初始化
```

### 为什么除 √10

10 维输入 × 10×32 矩阵 → 输出每个元素是 10 个 N(0,1) 变量的加权和 → 方差膨胀 10 倍 → 除 √10 后方差回到 1。保持输入输出数值尺度一致。

### P 的使用路径

| 路径 | 使用者 | 场景 |
|------|--------|------|
| `checkpoints/projection.npz` | `CandidateGenerator._load_projection_artifacts()` | 推理时元数据回退 |
| `KGEmbedder.__init__()` 自己算 | KGEmbedder | 训练/推理时构建 KG embedding |
| 预存向量直接读 | `CandidateGenerator._load_paper_embedding()` 优先级 1 | 主流路径，跳过 P |

### 完整流水线

```
10 维结构特征 (被引量/关键词数/作者数/年份等，有实际含义)
  → Z-score 标准化 (去量纲，所有维度 N(0,1))
  → 乘以 P (10×32) (线性混合，信息不丢失)
  → L2 归一化 (落到 32 维单位超球面)
  → paper.embedding (32 维向量)
```

### P 不参与训练

P 是固定随机矩阵，不参与梯度下降。原因：
- 随机投影有 Johnson-Lindenstrauss 理论保证：大概率近似保持距离关系
- 10→32 是升维，信息不丢失
- 没有监督信号来训练 P，固定 P 保证稳定性

## Q20: Actor-Critic 梯度下降方式（2026-06-02）（git: bad2152）

### 算法：TD(0) Actor-Critic

```python
# agent.py:93-163
# TD 误差
v_s  = critic(s)          # 当前状态估值
td_target = r + γ × critic(s') × (1 - done)   # 实际+预估 = 目标值
δ = td_target - v_s       # TD 误差

# Critic 更新：让估值更准
L_critic = δ²             # 最小化预测误差

# Actor 更新：好的多做，差的少做
L_actor = -log π(a|s) × δ.detach() - β × H(π)
          \_____________/           \______/
           策略梯度（用δ做乘数）      熵正则（防过早收敛）
```

### δ 的含义

| δ | 含义 | 对 Actor 的影响 |
|---|------|----------------|
| δ > 0 | 结果比预期好 | 增大这个动作的概率 |
| δ < 0 | 结果比预期差 | 减小这个动作的概率 |
| δ ≈ 0 | 符合预期 | 微调 |

### 训练循环

每 episode：reset 采样用户 → for step 1..50：Actor 选论文 → 环境模拟反馈 → 算 reward → 算 δ → 更新 Actor + Critic。300 episodes × 50 steps = 最多 15000 次更新。

### 两个优化器

Actor 和 Critic 各有独立的 Adam 优化器（lr=1e-3），各有独立梯度，通过 `δ.detach()` 切断联系——Actor 更新不反传 Critic。

## Q22: 推荐排序评估值的计算 + Actor 分数量级问题（2026-06-03）（git: bad2152）

### 原始公式

```
有 KG: final = 0.5 × actor_score + 0.3 × cos_sim + 0.2 × kg_score
无 KG: final = 0.6 × actor_score + 0.4 × cos_sim
```

### 量级差异问题

| 分量 | 来源 | 典型范围 | 均值 |
|------|------|---------|------|
| actor_score | softmax(N≈50) | 0.005 ~ 0.08 | 0.02 |
| cos_sim | L2 归一化后点积 | 0.0 ~ 1.0 | 0.5~0.7 |
| kg_score | KG 向量点积 | 0.0 ~ 1.0 | 0.3~0.5 |

Actor 名义权重 50%，实际贡献约 6%。因为 softmax 把 50 个概率压缩到均值 0.02，而另外两项轻松达到 0.5+。

### 真实影响

候选集被 `CandidateGenerator` 预筛选后，语义相似度挤在窄区间（0.65~0.75）。Actor 虽然绝对值小，但在相邻候选之间提供关键区分度。

## Q23: 排序归一化 + 质量门控方案（2026-06-03，✅ 已实现并上线）（git: c513ad2）

### 新排序流程

```
1. 计算三项原始得分
2. 质量门控（OR 逻辑）：cos_sim ≥ min_cos_similarity OR actor ≥ min_actor_score OR kg ≥ min_kg_score
3. 对通过门控的论文，逐项 min-max 归一化到 [0,1]
4. 加权求和 → 降序排列 → Top-K
```

### 改动文件

| 文件 | 操作 | 关键内容 |
|------|------|---------|
| `rl-service/config.py` | +2 配置项 | `min_cos_similarity=0.05`, `min_actor_score=0.001` |
| `rl-service/recommender/ranker.py` | 重写 | `_minmax_normalize()` + 门控→归一化→加权流程 |
| `docs/QA_2026-05-16_2026-06-02_v1.md` | +Q16 | 完整问题诊断、方案设计、边界处理、效果预期 |

### 边界处理

| 场景 | 策略 |
|------|------|
| 门控后 0 篇通过 | 打 warning，回退全量归一化 |
| 某项全等 (max==min) | 赋 0.5 中性分 |
| KG 不可用 | 自动退化为 0.6/0.4 权重 |

## Q25: 训练阶段 Actor 和 Critic 为什么能得出不同打分（2026-06-04）（git: bad2152）

### 核心差异

| 维度 | Actor | Critic |
|------|-------|--------|
| 看到论文？ | ✅ 是（concat state + paper→128维） | ❌ 否（只看 state→96维） |
| 输出 | N 个概率（每篇一个） | 1 个标量 V(s) |
| 损失函数 | `-log π × δ - βH` | `δ²` |
| 目标 | 最大化期望奖励 | 准确预测状态价值 |
| 更新信号 | td_error.detach() | 自身预测误差 |
| 推理时 | 决定推荐排序 | 不用 |

### 为什么必须分开

Actor 需要看到论文才能决策（"这篇该不该推"），Critic 评估的是"看到论文之前"的局面价值。如果 Critic 也看到论文特征，V(s) 会混入"已经知道要推什么了"的信息泄露 → td_error ≈ reward → 退化为普通 Policy Gradient → 失去 Actor-Critic 的加速收敛优势。

### 分离评估与决策

演员（Actor）负责演，评论家（Critic）负责评。演员需要知情才能演好，评论家需要置身事外才能客观。两者通过 TD 误差这座桥连接。

## Q26: 动作空间设计（2026-06-04）（git: bad2152）

### 定义

动作 = N 篇候选论文中的一个整数索引。`Categorical(probs)` 按概率采样。

```python
action ∈ {0, 1, ..., N-1}   # N = min(action_num, 实际候选数) ≈ 50
```

### 与传统 RL 的区别

| | 传统离散动作空间 | 本系统 |
|---|---------------|--------|
| 大小 | 固定 | 动态（30~50，随候选集变化） |
| 含义 | 固定（动作 3 永远是"开火"） | 变化（动作 3 这轮和下一轮是不同论文） |
| Actor 输出 | 固定 N 个 logit | 动态 N 个 logit |

### 训练 vs 推理

- **训练**：每步按 Categorical 分布随机采样一个动作 → 获取 reward → 更新。50% 概率论文可以探索到。
- **推理**：直接 `torch.topk(probs, k=10)` 取最高 K 个 → 进入 ranker 综合排序。

### Actor 为什么用 pairwise scoring

因为动作空间大小和内容每轮都在变，固定输出头没用。Actor 必须接受论文特征作为输入，动态判断"这篇匹配当前用户吗"。

## Q27: 论文拓扑关系如何变成张量（2026-06-04）（git: bad2152）

### 四步变换

```
Neo4j 图结构
  │
  ▼ _extract_structural_features() — 图遍历统计
10 维原始特征
  [cite_in, cite_out, kw_count, kw_reach, author_count,
   author_productivity, venue_popularity, co_author_density,
   topo_depth, recency]
  │
  ▼ Z-score — 全库均值和标准差归一化
  │
  ▼ 投影 P(10×32) — 固定随机矩阵
  │
  ▼ L2 归一化 → 32 维论文张量
paper.embedding
```

### 10 维特征提取（`_extract_structural_features`）

| 维度 | 含义 | 图遍历方式 |
|------|------|-----------|
| [0] cite_in | 被引次数 | 数 rev_adj 中 relation=="cite" 的边 |
| [1] cite_out | 引用次数 | 数 adj 中 relation=="cite" 的边 |
| [2] kw_count | 关键词数量 | 数 adj 中 has_keyword 边 |
| [3] kw_reach | 关键词连通度 | 对每个 has_keyword 边，查 rev_adj[keyword_id] 长度求和 |
| [4] author_count | 作者数量 | 数 rev_adj 中 author_of 边 |
| [5] author_productivity | 作者平均产出 | 对每个作者查 adj[author_id] 边数 / author_count |
| [6] venue_popularity | 场所影响力 | 对 publish_in 边，查 rev_adj[venue_id] 长度 |
| [7] co_author_density | 合著密度 | 作者间 co_author 边数 / 最大可能对数 |
| [8] topo_depth | 引用链深度 | BFS 沿 cite 出边，最深 5 层 |
| [9] recency | 新旧度 | (year-2010)/15 |

### 无 KG 时的回退

```python
# kg_embedder.py:199-242
```

## Q28: 学习路径计算 + 掌握度衰减 + 3D 力导向图（2026-06-04）（git: bad2152）

### 后端 → Python 数据流

```
VisualizationServiceImpl.buildKnowledgeGraph()
  ├─ 查用户历史论文的 AMiner ID
  ├─ POST /learning-path → Python
  │   ├─ PathBuilder.build_path()
  │   │   ├─ _extract_known_keywords(): 从历史论文提取关键词+频率
  │   │   ├─ get_keyword_cluster(): 查目标关键词的共现词+论文
  │   │   ├─ _build_path_nodes(): 构建 4 层路径节点
  │   │   │   depth=0: 已掌握关键词 (mastery=频率, 取前5)
  │   │   │   depth=1: 相关关键词 (未知的 mastery=0)
  │   │   │   depth=2: 目标关键词
  │   │   │   depth=3: 目标论文
  │   │   ├─ _build_path_edges(): 只连相邻深度层
  │   │   └─ coverage = 已知关键词∩相关关键词 / 相关关键词总数
  │   │
  │   └─ KnowledgePropagation
  │       ├─ batch_update(history): 按时间顺序批量传播
  │       │   time_weight = (i+1)/n  (越早读权重越低——遗忘)
  │       │   event_multiplier: read=1.0, favorite=1.5, write=2.0
  │       │
  │       ├─ update_mastery(paper_id, delta): 直接更新论文节点
  │       │
  │       └─ _propagate(node_id, delta, hop): 递归沿边扩散
  │           max_hops=3, decay=0.6 per hop
  │           边类型系数: has_keyword=0.8, cite=0.4, publish_in=0.3
  │           new_delta = delta × decay × rel_coeff × edge_weight
  │           delta < 1e-4 停止
  │
  └─ 返回 JSON: {nodes, edges, learningPath, pathNodes, pathEdges}
```

### 掌握度传播公式

```
mastery(neighbor) += delta_source × 0.6^hop × edge_type_coeff × edge_weight
```

### 颜色映射

```
mastery=0.0 → #3B82F6 (蓝)   未学习
mastery=0.5 → #F59E0B (橙)   学习中
mastery=1.0 → #10B981 (绿)   已掌握
```

### 3D 力导向图构建（`KnowledgeGraph.vue:153-293`）

| 步骤 | 操作 |
|------|------|
| 数据归一化 | 优先 pathNodes/pathEdges；边格式 src/dst → source/target |
| 分层布局 | `dagMode('td')` 自上而下，dagLevelDistance=50 |
| 节点渲染 | 关键词=球体（大小 4~5），论文=盒子（4×4×4）；color + emissiveIntensity 来自服务端 |
| 标签 | CanvasTexture sprite 浮在节点上方 |
| 路径播放 | setInterval 每步高亮 visited/active 节点+边，镜头自动追踪 |
| 交互 | 点击节点→镜头拉近+详情面板；点击背景→取消选中 |

## Q30: 线程池异步处理与推荐服务可靠性保障（2026-06-05）（git: bad2152）

### 线程池使用位置

项目中有 **3 处** 使用线程池/异步机制：

#### 1. Spring Boot 全局异步开关

```java
// ResearchApplication.java:10
@EnableAsync
public class ResearchApplication { ... }
```

声明式开启，让 `@Async` 注解生效。

#### 2. 专用线程池 Bean（`AppConfig.java:26-36`）

```java
@Bean("taskExecutor")
public ThreadPoolTaskExecutor taskExecutor() {
    executor.setCorePoolSize(4);           // 常驻 4 线程
    executor.setMaxPoolSize(8);            // 峰值 8 线程
    executor.setQueueCapacity(50);         // 等待队列 50
    executor.setThreadNamePrefix("async-rec-");
    executor.setRejectedExecutionHandler(
        new ThreadPoolExecutor.CallerRunsPolicy()  // 核心：队列满时调用线程自己跑
    );
}
```

线程池已就绪但当前 **无 `@Async` 的直接使用者**——这是一个预留能力，需要时在 Service 方法加 `@Async("taskExecutor")` 即可切入。

#### 3. Python 训练异步（`server.py:199-236`）

```python
@router.post("/train")
async def trigger_train(request, background_tasks: BackgroundTasks):
    def _run_train():
        train(config=config_copy, stop_controller=controller)

    background_tasks.add_task(_run_train)   # FastAPI 后台任务队列
    return TrainResponse(message="训练已在后台启动")
```

FastAPI `BackgroundTasks` 将训练丢到后台线程，API 立即返回。`_training_status` 全局变量作跨线程状态共享，`GET /model/info` 可实时查询进度。

### AppConfig 四层可靠性保障

#### 第一层：连接超时（5s）

```java
.setConnectTimeout(Timeout.ofMilliseconds(connectTimeout))  // 默认 5000ms
```

Python 进程挂了时不等操作系统默认 30s，5 秒就放弃——快速识别不可达。

#### 第二层：读取超时（10s）

```java
.setResponseTimeout(Timeout.ofMilliseconds(readTimeout))  // 默认 10000ms
```

Python 接收了请求但内部卡死时，10 秒没数据就断开。两超时合力：无论 Python 处于什么异常状态，调用方最多 ~15s 一定能拿到结果或异常。

#### 第三层：Apache HttpClient 连接池

```java
HttpClients.custom().setDefaultRequestConfig(requestConfig).build()
```

用 Apache HttpClient（带连接池）而非 JDK `HttpURLConnection`，TCP 连接可复用，避免高频调用时的端口耗尽和握手开销。

#### 第四层：CallerRunsPolicy

```java
executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy())
```

四种拒绝策略中唯一"不丢请求"的选择：

| 策略 | 队列满时行为 | 推荐场景 |
|------|------------|---------|
| `AbortPolicy` | 抛异常 | ❌ |
| `DiscardPolicy` | 静默丢弃 | ❌ |
| `DiscardOldestPolicy` | 丢最早 | ❌ |
| **`CallerRunsPolicy`** | 调用线程自己跑 | ✅ 慢但不丢 |

推荐请求是用户等待的结果——宁可慢不能让用户看空白页。

### PythonRecClient 的 try/catch 兜底

```java
public RecResponse getRecommendations(...) {
    try {
        return restTemplate.postForEntity(...).getBody();
    } catch (ResourceAccessException e) {  // 连接超时/被拒 → 命中第一层
        return null;
    } catch (Exception e) {               // 读超时/序列化异常 → 命中第二层
        return null;
    }
}
```

四个方法（`getRecommendations` / `triggerTraining` / `getLearningPath` / `getModelInfo`）**全部** try/catch → null/false，不向上抛异常。

### RecommendServiceImpl 的降级

```java
if (pyResp != null && pyResp.getRecommendations() != null) {
    items = assembleFromPython(pyResp.getRecommendations());     // 正常
} else {
    items = fallbackPopularRecommendations(k);                   // 降级
    // 返回本地热门论文，score=0.5，reason="推荐服务暂时不可用"
}
```

### 可靠性全景

```
用户请求
  → Tomcat 线程 → RecommendServiceImpl
      → PythonRecClient (RestTemplate: 连接池+5s/10s超时)
          ├── 成功 → 正常返回
          └── 异常 → return null
      → pyResp==null → fallbackPopularRecommendations()
          → 本地 paper 表热门论文 → "热门推荐（服务维护中）"
```

**五层防御：超时 + 连接池 + CallerRunsPolicy + try/catch null + 本地降级。即使 Python 完全宕机，用户仍看到推荐列表而非 500 错误。**

## Q31: 数据库三问（2026-06-05）（git: c513ad2）

### 问题 1：user_feature_snapshot 每条数据怎么来的？

**唯一写入路径**：`MySQLDataSource.cache_feature()` → `FeatureBuilder._build_features_from_mysql()`。

触发时机：每次推荐请求或训练 episode reset 时，`FeatureBuilder` 尝试从 MySQL 实时构建用户向量，构建完成后顺手写入缓存。

完整链路：

```
FeatureBuilder.get_user_features(user_id)
  → _build_features_from_mysql()
      │
      ├── 1. 尝试读缓存 (6h TTL)
      │      get_cached_feature("interest") + get_cached_feature("history")
      │      命中 → 直接返回，不写入
      │
      ├── 2. 缓存未命中 → 实时构建
      │      _build_interest_from_mysql() → 64-dim interest_vec
      │      _build_history_from_mysql()  → 64-dim history_vec
      │
      └── 3. 写入缓存
             cache_feature(user_id, "interest", interest_vec, "computed")
             cache_feature(user_id, "history",  history_vec,  "computed")
```

`cache_feature()` 使用 `INSERT ... ON DUPLICATE KEY UPDATE`（`mysql_data.py:118-127`），靠 `uk_user_type`（user_id + feature_type 唯一键）保证每个用户每种类型只有一条记录，重复构建时更新 `feature_vector` 和时间戳。

TTL 逻辑在 `get_cached_feature()`（`mysql_data.py:93-110`）：

```sql
WHERE user_id = %s AND feature_type = %s
  AND updated_at >= NOW() - INTERVAL 6 HOUR
```

超过 6 小时的缓存视为过期，重新构建。

**缓存来源标记**：所有自动构建的特征 source 标记为 `"computed"`。seed 数据中已有 4 个用户的预填记录（user 1/2/6/7/8/9/3/10/5 共 9 个用户各有 interest+history 两条，即表中有 18 条记录，编码到 snapshot id 1~46）。

```sql
-- 批量查询同角色用户的兴趣标签，计算与当前用户的重叠度
SELECT u.id as user_id,
       COUNT(DISTINCT h1.interest_tag) as overlap_count
FROM user u
JOIN user_interest_history h1 ON u.id = h1.user_id
WHERE u.role = ?                          -- 同角色
  AND u.id != ?                           -- 排除自己
  AND u.id NOT IN (联系人列表)              -- 排除已有联系人
```

## Q33: 用户兴趣向量为何算 64 维再截 32 维（2026-06-05）（git: bad2152）

### 原因：64 维是"全特征空间"，32 维仅是状态内部的分割

`FeatureBuilder` 内部一切工作在 `base_state_dim=64` 维度：`_hash_tag(tag, 64)` → 64 维单位向量；`_paper_attr_vec(paper)` → 硬编码 64 维词袋向量；`_build_interest_from_mysql()` → 64 维兴趣向量；`_build_history_from_mysql()` → 64 维历史向量。

但同一份 64 维向量有两个消费者：

| 消费者 | 使用的维度 | 位置 |
|--------|-----------|------|
| **Actor 状态拼接** | 前 32 维 | `build_state()`: `interest[:32] + history[:32]` |
| **候选检索余弦相似度** | 完整 64 维 | `CandidateGenerator.generate(user_embedding=interest_vector)`（完整 64 维点积检索） |
| **排序余弦相似度** | 完整 64 维 | `ranker.rank()`: `base_state[:64] @ topic_matrix` |

如果直接算 32 维，候选检索和排序的余弦相似度只能在 32 维空间做——hash 桶减半，每个桶的碰撞概率翻倍，区分度下降。算 64 取 32 让检索用高分辨率空间，状态只取前一半。`build_item_vector()` 也返回完整 64 维（`_pad_to_base_dim` 将 32 维论文 embedding 后补零到 64），确保 topic_vector 与 interest_vector 维度对齐。

## Q36: 行为向量与KG向量的区别 + 兴趣向量hash机制分析（2026-06-05）（git: bad2152）

### 行为向量 vs KG 向量

| | 兴趣向量 | 历史行为向量 | KG 向量 |
|---|---|---|---|
| **来源** | `user_interest_history` 标签 | `behavior_log` 中论文的 embedding | Neo4j 图结构的 KG embedding |
| **构建** | 标签→hash→单位向量→加权平均 | 论文32维预存向量→行为加权池化 | 论文10维图特征→Z-score→P(10×32)→均值池化 |
| **权重** | weight(注册写0.5, seed有0.5~5.0) | click=0.5, read=1.0, favorite=2.0, 每60s+0.5(上限+2.0) | 无权重，直接均值 |
| **含义** | "用户声称对什么感兴趣" | "用户实际读了什么论文" | "用户读的论文在图谱中处于什么位置" |
| **更新** | 注册/编辑资料时一次性 | 每次行为实时 | 随历史列表实时重算 |

### 兴趣向量 hash 机制

`_hash_tag(tag, dim)` 将标签字符串 → `hash()` → 32-bit int 种子 → PRNG → dim 个 N(0,1) 数 → L2 归一化。**确定性但无语义**：同一标签每次相同向量，不同标签不同向量。共享标签的用户向量有共同分量（余弦相似度>0），无交集标签的用户接近正交。这种技术叫**随机索引（Random Indexing）**。

**局限性**：标签间无语义距离（"Deep Learning"和"Reinforcement Learning"与"Deep Learning"和"Quantum Physics"的关系相同）。本项目通过注册时强制从 Neo4j 46 个 Keyword 节点选择来规避"NLP"与"Natural Language Processing"不匹配问题。改进方向（暂不实施）：从 KG 关键词共现矩阵学语义 embedding，或通过关联高被引论文用 `paper.embedding` 均值替代 hash。

## Q37: 密码加密机制与测试账号密码（2026-06-07）（git: c513ad2）

### 加密机制

使用 Spring Security `BCryptPasswordEncoder`（strength=10，哈希前缀 `$2a$10$`）。注册时 `passwordEncoder.encode()` 加密存储，登录/改密时 `passwordEncoder.matches()` 校验。关键代码：

```java
// SecurityConfig.java:97-98
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}

// UserServiceImpl.java:47 — 注册
user.setPassword(passwordEncoder.encode(request.getPassword()));

// UserServiceImpl.java:77 — 登录校验
passwordEncoder.matches(request.getPassword(), user.getPassword())

// UserServiceImpl.java:226-229 — 改密
if (!passwordEncoder.matches(req.getOldPassword(), user.getPassword()))
    throw ...;
user.setPassword(passwordEncoder.encode(req.getNewPassword()));
```

新增 `PUT /api/user/password` 端点（`UserController.java`），接受 `{oldPassword, newPassword}`，需要旧密码验证。

### 历史问题

id 1–10 全部使用**完全相同的 BCrypt 哈希值**——SQL 脚本中将同一个预计算哈希复制粘贴的结果，而非逐个调用 `encode()` 生成。这导致所有老用户共享同一密码 `admin123`。实际注册的新用户（如 student_zhao）每次产生独立的 salt 和哈希。
