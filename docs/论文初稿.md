# 基于知识图谱与强化学习的科研成果推荐系统

## 摘要

随着学术研究成果的爆发式增长，科研人员面临严重的信息过载问题——每年有数百万篇新论文发表，传统的关键词检索和被动订阅已难以满足研究者高效发现相关文献的需求。本文针对科研推荐场景中用户兴趣动态演化、学术知识存在结构化关联、推荐结果需要可解释性等特点，设计并实现了一套基于知识图谱与强化学习的科研成果推荐系统。系统采用"前端-业务后端-推荐微服务"三层分离架构，以Spring Boot为业务中枢、FastAPI为算法服务载体、Vue 3为交互前端。在推荐算法层面，本文将知识图谱结构特征嵌入强化学习状态空间，利用Actor-Critic架构对候选项进行序列化排序决策，并引入多因素加权奖励函数平衡即时反馈与长期科研价值。此外，系统基于知识图谱的拓扑关系实现了学习路径生成与推荐解释功能。工程实现上，系统采用MySQL与Neo4j双库协同的数据策略，通过JWT无状态认证保障安全，并通过SockJS/STOMP实现实时私信协作。测试结果表明，系统各模块功能完整，推荐链路响应时间可控，降级机制保障了服务可用性。

**关键词：** 推荐系统；知识图谱；强化学习；Actor-Critic；微服务架构

## 1 引言

### 1.1 研究背景

学术出版物的数量正以指数级速度增长。据IEEE Xplore、ACM Digital Library等主流数据库的统计，每年新增的计算机科学领域论文超过十万篇[1]。面对海量的学术信息，研究者传统的文献获取方式——基于关键词的检索和期刊会议订阅——已越来越难以满足高效、精准的文献发现需求。研究者通常需要花费大量时间在不同数据库中进行反复检索、筛选和阅读，这一过程低效且容易遗漏跨领域的潜在相关研究[2]。

推荐系统作为解决信息过载问题的有效手段，在电子商务、社交媒体、内容分发等领域取得了显著成功。协同过滤、基于内容的推荐、深度学习推荐等技术被广泛应用于各类商业场景[3]。然而，科研推荐场景具有与上述消费场景截然不同的特征：（1）用户的研究兴趣是动态变化的——研究者可能从强化学习转向图神经网络，或在不同课题之间切换，推荐系统需要捕捉这种兴趣演化过程而非仅依赖历史行为；（2）学术知识之间存在丰富的结构化关系——引用关系、合作关系、主题关联等构成了天然的学术知识图谱，蕴含了内容相似度无法表达的深层语义[4]；（3）推荐结果需要可解释性——研究者不仅关心"推荐了什么"，更关心"为什么推荐这个"，以便评估推荐的可信度和相关性；（4）推荐应当服务于研究者的长期学术成长，而非仅优化短期点击率[5]。

### 1.2 现有方法的不足

传统推荐系统在科研场景下存在若干局限。协同过滤方法依赖用户-物品评分矩阵的静态分析，难以捕捉用户兴趣的动态变化过程，且面临严重的冷启动问题[6]。基于内容的推荐虽然可以通过论文的文本特征计算相似度，但仅依赖文本信息无法充分利用学术知识网络中的结构关系——两篇论文即使文本表达不同，只要位于相同的引用链或作者合作网络中，也可能对同一研究者具有高度相关性。深度学习方法如基于Transformer的序列推荐虽然能够建模用户行为序列，但其通常作为"黑箱"模型运行，难以输出结构化的推荐理由[7]。

在系统架构层面，传统的单体推荐系统将推荐算法与业务逻辑紧密耦合，导致算法迭代时需要整体重新部署，不利于推荐模型的独立优化和快速实验。此外，大多数现有的学术推荐工具（如Google Scholar的推荐功能、ResearchGate的论文推送）仅提供单向的推荐结果展示，缺乏对"用户应当如何循序渐进地进入一个新研究领域"这类学习路径问题的支持。

### 1.3 本文目标与贡献

本文从软件工程视角出发，设计并实现了一个基于知识图谱与强化学习的科研成果推荐系统。系统以学术知识图谱为语义基础设施，以Actor-Critic强化学习为推荐决策引擎，构建了从前端交互到后端业务逻辑再到推荐微服务的完整工程链路。本文的主要贡献包括：

（1）提出了一种融合知识图谱结构特征的强化学习推荐方法，将用户状态建模为兴趣向量、行为向量和图结构向量的拼接，使得推荐决策能够同时利用内容语义和学术网络的结构信息。

（2）设计了MySQL与Neo4j双库协同的数据架构，以AMiner ID为跨库统一标识，实现了关系型业务数据与图结构学术数据的高效协作。

（3）在推荐功能之外，基于知识图谱的拓扑关系实现了学习路径生成功能，将"推荐论文"提升为"规划学习路线"。

（4）完成了前后端分离的完整系统工程实现，包含JWT鉴权、行为日志追踪、实时私信、社区协作等功能模块，并设计了推荐服务的降级策略以保障系统可用性。

## 2 相关工作与文献综述

### 2.1 推荐系统技术演进

推荐系统经历了从协同过滤到深度学习再到强化学习的技术演进。传统协同过滤方法[8]通过矩阵分解学习用户和物品的隐向量，在Netflix Prize等竞赛中取得了良好效果，但其对静态评分矩阵的依赖限制了其在动态场景中的应用。基于深度学习的推荐方法[9]利用神经网络捕捉用户与物品之间的非线性交互，如Neural Collaborative Filtering（NCF）将矩阵分解推广为可学习的神经网络结构。然而，这些方法通常将推荐视为独立的预测任务，忽略了推荐过程中的序列决策特性。

### 2.2 强化学习在推荐中的应用

将推荐过程建模为马尔可夫决策过程（MDP）是近年来推荐系统领域的重要研究方向[10]。在强化学习框架下，推荐智能体在每个时间步根据用户状态选择一个推荐动作，环境返回奖励信号并转移到下一状态。这种建模方式自然契合了科研推荐的序列化特征——研究者与系统持续交互，当前推荐会影响后续的知识获取和行为选择。Actor-Critic算法[11]结合了策略梯度（Actor）和价值估计（Critic）的优势，通过TD误差驱动策略网络和价值网络的同步更新，在平衡探索与利用方面具有理论优势。

### 2.3 知识图谱增强推荐

知识图谱作为一种结构化的语义网络，近年来被广泛用于增强推荐系统的表示能力和可解释性[12]。知识图谱将物品及其属性建模为图中的节点和边，可以捕捉物品之间超越共现统计的语义关系。在推荐中利用知识图谱的典型方法包括：基于路径的方法（如PER、MetaPath）利用元路径抽取用户-物品之间的连接模式[13]；基于嵌入的方法（如TransE、TransR、KGAT）将图谱结构和实体嵌入联合学习。本文综合了上述思路——使用知识图谱嵌入作为强化学习状态的组成部分，同时利用图拓扑关系实现推荐解释和学习路径生成。

### 2.4 微服务架构与推荐系统工程化

从软件工程角度，将推荐算法作为独立微服务部署已成为工业界的主流实践[14]。微服务架构使推荐模块可以独立开发、测试、部署和扩展，算法工程师可以专注于模型优化而不必关心业务系统的实现细节。Spring Boot与Spring Cloud为Java生态中的微服务开发提供了成熟的基础设施，FastAPI则为Python机器学习服务提供了高性能的异步API框架[15]。本文的架构设计借鉴了这些工业实践，将业务后端与推荐微服务解耦，通过HTTP API实现同步调用和异步训练触发。

### 2.5 研究缺口总结

综合上述分析，当前研究存在以下可改进之处：（1）强化学习推荐在科研场景的工程落地较少，多数研究停留在仿真实验阶段；（2）知识图谱与强化学习推荐的结合多聚焦于算法层面，缺乏从系统架构角度的工程实践论述；（3）推荐系统与学习路径规划功能的协同设计鲜有讨论。本文的工作正是针对这些缺口，从软件工程视角提供完整的系统设计与实现方案。

## 3 系统分析与设计

### 3.1 需求分析

#### 3.1.1 功能需求

本系统的目标用户群体为科研人员（研究生、教师、研究员等），核心功能需求包括：

**（1）论文检索与浏览：** 用户可以通过关键词搜索论文，按年份、会议/期刊、研究领域筛选结果，查看论文详情（标题、摘要、作者、关键词、被引量等），并下载论文文本。

**（2）个性化推荐：** 系统根据用户的历史阅读和收藏行为，自动生成Top-K个性化论文推荐。推荐结果应包含推荐理由、相似度评分和置信度，使用户能够理解决策依据。

**（3）行为日志记录：** 系统记录用户的点击、收藏、阅读时长等交互行为，这些行为数据既是推荐模型的输入来源，也是未来离线训练和评估的数据基础。

**（4）知识图谱可视化：** 系统以三维力导向图的形式展示学术知识图谱，支持节点交互、逐层展开和学习路径高亮，帮助用户直观理解学术领域的概念结构。

**（5）学习路径生成：** 系统根据用户当前的知识储备和目标研究方向，在知识图谱中规划一条从基础知识到前沿论文的渐进式学习路线。

**（6）社区协作与实时私信：** 用户可以在社区中发布帖子、评论他人观点，管理员可审核帖子内容。实时私信功能支持研究者之间的一对一文本交流。

**（7）用户管理与权限控制：** 系统支持四种角色（游客、学生、研究者、管理员），不同角色拥有差异化的访问权限。管理员可以审核帖子、导入论文数据、管理用户角色、触发模型训练。

**（8）管理后台：** 管理员可通过专用后台界面执行帖子审核、用户角色管理、论文批量导入和推荐模型训练触发等操作。

#### 3.1.2 用例分析

系统的主要参与者为四类用户：游客（未登录访客）、学生用户、研究者用户和管理员。核心用例包括：

**游客用例：** 注册账号、登录系统、浏览搜索结果、查看论文详情。

**学生/研究者用例：** 获取个性化推荐、记录行为反馈、管理个人资料与研究方向、收藏论文、查看知识图谱与学习路径、参与社区讨论、收发实时私信。

**管理员用例：** 除具备研究者全部权限外，还包括审核社区帖子、管理用户角色、批量导入论文数据、触发推荐模型训练。

#### 3.1.3 关键服务交互

**推荐服务交互流程（顺序图描述）：** 前端发起GET /api/recommend请求 → RecommendController接收请求并从JWT中提取用户ID → RecommendServiceImpl查询behavior_log获取用户历史行为 → 通过PaperMapper将本地论文ID批量转换为AMiner ID → PythonRecClient向Python推荐服务POST /recommend发送用户ID、推荐数量和AMiner ID历史列表 → Python推荐服务执行特征构建、候选召回、Actor-Critic排序、解释生成 → 返回排序后的推荐论文列表（含评分和理由） → RecommendServiceImpl通过PaperService.getByAminers()补全论文的完整业务字段（标题、作者、年份、摘要等） → 组装RecommendResponse返回前端渲染。若Python服务调用失败，自动降级为热门论文推荐。

**学习路径生成流程（活动图描述）：** 前端发起POST /learning-path请求 → FastAPI接收包含用户ID、目标主题、阅读历史和最大节点数的请求体 → PathBuilder从知识图谱中提取用户已知关键词并计算掌握度 → GraphQuery获取目标主题的关键词簇和相关论文 → 按深度层组织路径节点（已掌握关键词→相关关键词→目标关键词→目标论文） → 在连续深度层级间建立加权边 → 估算学习时长并计算覆盖率 → 返回序列化路径数据 → 前端通过Three.js三维图谱和学习路径面板可视化展示。

**实时私信流程（顺序图描述）：** 前端通过SockJS连接/ws-messages端点 → STOMP客户端订阅/user/queue/private（个人消息队列）和/topic/user-status（在线状态） → 发送消息时向/app/send-private发布STOMP消息（消息体中包含JWT令牌） → MessageWebSocketController解析令牌获取发送者身份 → PrivateMessageServiceImpl将消息持久化到MySQL → 通过SimpMessagingTemplate.convertAndSendToUser()推送到接收者的个人队列 → 接收者前端实时渲染新消息。

### 3.2 架构设计

#### 3.2.1 整体架构

本系统采用"前端-业务后端-推荐微服务"三层分离架构，各层的职责与技术选型如下：

**表示层（Vue 3 + Vite + Element Plus）：** 负责用户界面渲染和交互逻辑，通过Axios实例统一访问后端API。采用Pinia进行客户端状态管理，Vue Router实现页面路由和导航守卫。知识图谱可视化采用Three.js与3d-force-graph实现三维力导向图渲染，统计图表采用Chart.js。实时消息采用SockJS + STOMP协议实现WebSocket通信。

**业务层（Spring Boot 3.2 + MyBatis-Plus）：** 作为系统的业务中枢，负责JWT鉴权与权限控制、REST API接口暴露、数据库事务管理、行为日志记录、社区帖子管理、私信持久化等业务逻辑。对Python推荐服务的调用通过PythonRecClient封装，采用RestTemplate进行HTTP同步调用，所有调用均设有超时和异常降级处理。

**算法层（FastAPI + Python）：** 作为独立的推荐微服务，负责强化学习推荐推理、知识图谱加载与嵌入、候选召回与排序、推荐解释生成、学习路径构建以及模型训练。推荐服务与业务后端通过HTTP API松耦合，可独立部署、升级和扩展。

**数据层：** 采用MySQL存储用户、权限、行为日志、社区帖子、私信等事务型业务数据；采用Neo4j图数据库存储学术知识图谱（论文、作者、关键词、会议/期刊节点及引用、归属等关系）。两端以AMiner论文标识作为统一关联键，实现双库协同。

#### 3.2.2 技术选型理由

**为何选择Spring Boot而非其他Java框架：** Spring Boot 3.2提供了成熟的企业级应用开发基础设施，其自动配置、起步依赖和嵌入式服务器大幅减少了项目搭建的样板代码。相比Jakarta EE的传统部署模式，Spring Boot的内嵌Tomcat更适合快速原型开发和演示部署。Spring Security提供了完整的认证与授权框架，其过滤器链架构可以自然集成JWT无状态认证。

**为何选择FastAPI而非Flask或Django：** FastAPI基于Python异步编程模型（asyncio），原生支持高并发的HTTP请求处理，适合作为推荐推理服务的API框架。其自动生成的OpenAPI文档便于与Java后端进行接口联调。Pydantic的数据校验机制保证了输入输出的类型安全。相比Flask，FastAPI的异步能力更适合IO密集型的推荐推理场景；相比Django，FastAPI更轻量且不包含不必要的ORM层。

**为何选择MyBatis-Plus而非JPA/Hibernate：** MyBatis-Plus保留了原生SQL的灵活性，适合处理系统中复杂的查询需求（如论文全文搜索、聚合查询等）。其代码生成器和Lambda查询包装器减少了常规CRUD的样板代码。对于以MySQL为主的业务数据层，MyBatis-Plus提供的分页插件、乐观锁插件和逻辑删除功能覆盖了常见的数据库操作需求。

**为何选择Neo4j作为图数据库：** 学术知识图谱天然具有图结构特征——论文、作者、关键词、会议/期刊是不同类型的节点，引用、归属、合作是不同类型的边。关系型数据库需要多次JOIN才能表达多层图遍历查询，而Neo4j的原生图存储和Cypher查询语言可以直接表达"查找与某论文共享关键词且被同一作者引用的论文"这类图模式。此外，Neo4j的MERGE语义天然支持数据导入中的"存在即更新、不存在即插入"逻辑，简化了图数据的增量同步。

### 3.3 数据库设计

#### 3.3.1 MySQL关系型数据库

系统在MySQL中维护以下主要数据表：

**user（用户表）：** 存储用户账户信息。核心字段包括id（自增主键）、username（唯一用户名）、password（BCrypt加密密码）、email（邮箱）、role（角色：STUDENT/RESEARCHER/ADMIN）、avatar（头像URL）、bio（个人简介）、research_interests（研究方向，逗号分隔字符串）、deleted（逻辑删除标记）、create_time、update_time。

## 4 关键模块实现

### 4.1 推荐服务核心算法

#### 4.1.1 状态空间设计

强化学习推荐的状态向量由三部分拼接构成：

$$s_t = [interest\\_vector; history\\_vector; kg\\_vector]$$

其中interest_vector（32维）表示用户当前的研究兴趣分布，由用户近期交互论文的关键词和主题分布聚合得到；history_vector（32维）表示用户历史行为的时序特征，通过行为日志中的交互序列构建；kg_vector（32维，可选）表示用户在知识图谱中的结构位置，由KGEmbedder对用户交互论文的图邻居特征进行聚合得到。当启用知识图谱时，状态总维度为96维；未启用时为64维。

#### 4.1.2 Actor-Critic架构

系统的推荐决策采用Actor-Critic强化学习架构，由两个神经网络协同工作：

**Actor（策略网络，π(a|s)）：** 以当前状态s_t为输入，输出候选论文集合上的归一化概率分布。网络结构为输入层→128维隐藏层（ReLU激活）→输出层（softmax），输出维度等于候选动作数（默认为20）。Actor回答的核心问题是"在当前用户状态下，推荐哪篇论文最合适"。

**Critic（价值网络，V(s)）：** 以当前状态s_t为输入，输出该状态的标量价值估计。网络结构为输入层→128维隐藏层→1维输出。Critic回答的核心问题是"当前状态未来预期可以获得多少累积奖励"。

模型通过TD(0)方法进行在线更新。定义TD误差为：

$$\delta_t = r_t + \gamma V(s_{t+1}) - V(s_t)$$

其中γ为折扣因子（默认0.99），r_t为即刻奖励。Critic通过最小化δ²更新参数，Actor通过最大化log π(a_t|s_t) × δ更新参数。此外，损失函数中引入熵正则化项α × H(π(·|s))（α=0.01），以鼓励策略保持一定的探索性，避免过早收敛到单一推荐模式。

#### 4.1.3 多因素奖励函数

奖励信号由多个因素加权组合而成，以兼顾用户的即时反馈和长期科研价值：

$$r_t = \alpha \cdot click + \beta \cdot favorite + \gamma \cdot duration + \delta \cdot topic\\_match + \eta \cdot long\\_term + \zeta \cdot kg\\_topology$$

各权重默认值依次为1.0、2.0、0.5、3.0、1.5、2.0，分别对应点击、收藏、阅读时长、主题匹配度、长期科研价值和知识图谱拓扑相关度。收藏行为和主题匹配度被赋予较高权重，因为其比点击更能反映真实的研究兴趣。

#### 4.1.4 候选召回与最终排序

系统采用"召回→排序"两阶段架构。候选召回阶段由CandidateGenerator负责，支持三种策略：similarity（基于用户兴趣与论文向量的相似度召回）、popular（按被引量召回热门论文）、hybrid（混合策略，默认选项）。召回阶段将论文全库缩减为20个候选，排序阶段再由融合分数进行精细排序。最终排序分数的计算公式为：

$$final\\_score = 0.5 \times actor\\_score + 0.3 \times similarity + 0.2 \times kg\\_topology$$

若知识图谱未启用，则退化为Actor分（0.6）与语义相似度（0.4）的加权组合。

### 4.2 学习路径生成算法

学习路径生成是推荐功能的自然延伸，目标是为用户规划一条从现有知识储备到目标研究方向的渐进式学习路线。

**算法核心流程（PathBuilder.build_path）：**

步骤1——提取用户已知关键词：从用户历史阅读论文中提取关键词集合，标记为"已知关键词"，掌握度初始化为高值（0.8-1.0）。

步骤2——获取目标主题簇：通过GraphQuery在知识图谱中执行子图遍历，获取与目标主题关键词通过has_keyword、cite、publish_in等关系相连的关键词簇和相关论文集合。

步骤3——按深度组织路径节点：将收集到的节点按知识层级分为四层——已掌握关键词（深度0）、相关关键词（深度1）、目标关键词（深度2）、目标论文（深度3）。节点之间仅允许跨深度层连接，不允许同层连接，以保证路径的渐进性。

步骤4——构建加权边：在连续深度层级之间建立有向边，边权重随深度距离衰减。衰减公式为：

$$w(u, v) = \frac{1}{depth(v) - depth(u) + 1}$$

步骤5——估算学习时长和覆盖率：总学习时长 = 路径中论文节点数 × 2小时；覆盖率 = 已知关键词数 / 总相关关键词数。

**掌握度传播算法（KnowledgePropagation）：** 当用户完成路径上某个节点的学习后，以该节点为起点进行多跳掌握度传播。一阶传播直接邻居获得Δmastery × edge_weight的掌握度增量；二阶传播在此基础上乘以衰减因子0.6；三阶传播继续衰减。传播最大跳数为3跳，最小增量为1e-4以防止无限微小传播。

### 4.3 降级与容错设计

系统在多个层面设计了容错机制。在推荐服务的调用层面，PythonRecClient的所有方法均包裹在try-catch块中：连接超时（ResourceAccessException）或任意异常（Exception）均返回null而非向上传播，调用方根据返回值是否为null判断服务可用性。当推荐服务不可达时，RecommendServiceImpl自动切换到fallbackPopularRecommendations()方法，返回按被引量排序的热门论文作为降级推荐，确保前端用户始终能看到推荐结果。降级推荐的score统一设为0.5，confidence设为0.3，并在recommendation.reason中明确标注"推荐服务暂时不可用，展示高被引论文"。

在WebSocket消息层面，前端实现了乐观追加策略：发送消息时先将消息追加到本地消息列表，若服务端确认失败则回滚并标记为发送失败状态，避免用户感知延迟。

### 4.4 前后端安全通信

系统采用JWT无状态认证方案。用户登录成功后，后端在JwtUtil中生成包含userId、username和role的签名令牌，前端将令牌存储在localStorage中。后续所有API请求通过Axios请求拦截器自动在Authorization头中附加Bearer令牌。后端JwtFilter在每次请求时从Authorization头提取并验证令牌，将解析出的userId设置到SecurityContextHolder中，使得控制器层可通过(Long) authentication.getPrincipal()直接获取当前用户ID。SecurityConfig中定义了白名单路径（登录、注册、论文公开查询等）与角色限制路径（/api/admin/**仅ADMIN可访问），并在异常处理中返回统一的JSON格式401/403响应。

WebSocket端点的鉴权独立于HTTP鉴权：/ws-messages/**路径在SecurityConfig中被标记为permitAll，实际鉴权在MessageWebSocketController中从STOMP消息体提取JWT令牌进行二次验证。

## 7 结论

### 7.1 工作总结

本文从软件工程视角出发，设计并实现了一套基于知识图谱与强化学习的科研成果推荐系统。系统采用三层分离架构，将Vue 3前端、Spring Boot业务后端和FastAPI推荐微服务解耦，实现了推荐算法的独立迭代与部署。在推荐算法层面，本文将知识图谱结构特征融入强化学习状态空间，通过Actor-Critic架构进行序列化推荐决策，并设计了多因素加权奖励函数以平衡即时反馈与长期科研价值。在工程实现层面，本文完成了MySQL与Neo4j双库协同的数据架构设计、JWT无状态认证方案、行为日志驱动的推荐上下文构建、实时私信的SockJS/STOMP实现以及推荐服务的降级容错机制。此外，基于知识图谱的拓扑关系实现了学习路径生成功能，将推荐从"论文检索"提升为"学习规划"。

### 7.2 创新点

（1）将知识图谱结构特征与强化学习状态空间融合，使推荐决策同时利用内容语义和学术网络的结构信息。
（2）设计了MySQL与Neo4j双库协同的数据架构，通过Aminer ID统一标识实现了关系型业务数据与图结构学术数据的高效协作。
（3）在推荐功能之上扩展了学习路径生成功能，实现了从"推荐论文"到"规划学习路线"的功能升级。

### 7.3 局限性与未来工作

本系统存在以下局限性：（1）强化学习训练环境当前仍以仿真数据为主，尚未完全接入真实用户行为序列进行端到端在线训练；（2）候选召回阶段尚未集成大规模向量检索引擎（如Faiss、Milvus），当前召回策略适用于中小规模论文库；（3）缺乏系统的离线评估和在线A/B测试框架来量化推荐质量；（4）用户画像构建主要依赖显式研究方向输入和行为日志，尚未充分利用论文全文的深度语义信息。

未来工作将围绕以下方向展开：（1）接入真实学术行为数据构建离线训练集，并在仿真环境中进行策略预训练后再迁移到在线环境；（2）集成Faiss或Elasticsearch实现大规模候选召回，突破当前内存召回的上限；（3）建立包含Precision@K、Recall@K、NDCG、多样性和覆盖率在内的多维度评估体系；（4）引入大语言模型增强推荐解释的自然语言生成质量，使解释文本更加个性化和可读。
